## ⚡ Router-based block recovery (2026-08-23, CONFIRMED WORKING) — faster alternative to power-cycling

The user's router admin panel (`http://192.168.1.1/`, already logged in as admin, no credentials needed) has an **"Internet Access" toggle** under the "Internet Access" card. Turning it OFF then back ON forces a new DHCP lease (new WAN IP), which can clear an eToro/Cloudflare block the same way a physical router power-cycle does — but faster and without the user needing to physically unplug anything.

**Critical safety constraint discovered**: this router page is on the LAN (always reachable via Claude-in-Chrome regardless of WAN state), but toggling "Internet Access" OFF cuts the WAN link that carries **the orchestrating Claude session's own connection to Anthropic's cloud** — not just the browser extension's. If you send the OFF click and then wait for a fresh instruction from the cloud to send the ON click, that fresh instruction may never arrive (the WAN is down), stranding the user offline with no way for Claude to recover it remotely. **Never split OFF and ON into two separate round-trips.**

**The safe pattern**: queue OFF → wait → ON as a **single `browser_batch` call** (one round-trip to the Chrome extension). Once the extension receives the batch, it executes all steps locally in the browser without needing another cloud round-trip mid-sequence — so it should complete the full cycle even during the brief WAN blip. Toggle coordinates: click the same toggle switch position twice (first click = OFF, second click after a wait = back ON, since it's a single switch, not two buttons). Observed: the router can take several seconds in a "DHCP connecting" state after toggling — use a generous wait (~8-10s) between the OFF and ON clicks in the batch, tuned by testing since this is unconfirmed as of this writing.

**Status: CONFIRMED working, 2026-08-23.** Live test: clicked the toggle at `[985, 122]` (coordinates specific to that session's screenshot/viewport — re-locate via a fresh screenshot or `find`, don't hardcode), waited 8s, clicked again, all in one `browser_batch` call. Result: WAN IP changed (46.121.144.42 → 46.121.144.46), "Internet Access" showed ON again automatically. A transient "Claude in Chrome is not connected" / tool-timeout did occur mid-sequence (expected — that's the WAN blip) but resolved on its own within ~10-15s once the new IP was established; no manual intervention was needed.

**How to use this**: navigate to `http://192.168.1.1/` (works instantly if already logged in as admin this session; if it shows a login form, the admin session expired and only the user can re-authenticate — do NOT enter any username/password yourself, ask the user to log back in first). Locate the "Internet Access" toggle via a screenshot, then one `browser_batch`: click toggle → `wait` ~8s → click toggle again → `wait` ~2s → screenshot to confirm WAN IP changed. If a tool call errors with "not connected" or "did not respond in time" immediately after, that's expected — wait a few seconds and retry a light check (`get_page_text`) rather than panicking; it recovers on its own.

**Still true**: never split the OFF and ON clicks across two separate tool-call round-trips — always one `browser_batch`. And the router's own admin login session can independently expire (seen once), which is a separate failure mode from the WAN blip — if that happens, ask the user to re-authenticate, don't enter credentials yourself.

## If you hit a block: stop, don't solve, checkpoint, report

Three signatures, all handled the same way — **never attempt to solve/bypass any of them, never attempt to log in yourself**:

1. **Ordinary lockout**: "It looks like something went wrong" dialog + sidebar flips to logged-out ("Have an account? / Sign in") + price label shows "Delayed prices". Most common, usually clears with a genuine user re-login.
2. **CAPTCHA**: an explicit "Slide right to secure your access" / "Automated (bot) activity" challenge. Rarer, more severe.
3. **Cloudflare ban**: "Error 1015: You are being rate limited" page, appears before eToro's app even loads, has a Ray ID/timestamp. Not a login issue — no login/CAPTCHA widget present. Has cleared in as little as ~12 minutes in practice; don't assume a fixed wait time, but don't hammer it either.

On any of these: stop immediately, do not retry, checkpoint your files accurately (exact last ticker done), report back which signature you saw. **The block does not reliably clear just by waiting** — the user needs to actually disconnect the internet and power-cycle the router/modem (unplug from electricity) to get a fresh IP before it clears. A monitoring loop can periodically check whether it's cleared, but can't make that happen — the user has to take that physical action. Say so explicitly when reporting a block, don't imply "just wait."

**Always rigorously verify the login precondition before starting real work** — navigate to `https://www.etoro.com/markets/aapl/research` and confirm ALL of: account menu (not "Login" link), green Trade button, "Prices by NASDAQ" (not delayed), working Analysis tab with real numbers (e.g. AAPL should show ~245/337/400 Low/Avg/High). A user saying "continue"/"logged in" is not proof — your own check is the real gate. This has caught real problems before (a session once found the account still logged out despite the user believing otherwise).

## Take Profit tooltip fix (2026-08-30)

Fixed a bug where the portfolio "Take Profit" hover tooltip rendered with correct layout but was invisible/unclickable — the Copy & Open on eToro button couldn't be clicked. Root cause: `.pf-tooltip` was `position: absolute` inside the sticky (frozen) ticker column; `.table-wrap`'s `overflow-x: auto` forces `overflow-y` to compute as `auto` too, and combined with the sticky column's table-cell stacking, Chrome refused to paint the tooltip above sibling rows. Fixed by switching `.pf-tooltip` to `position: fixed` ([part1_fixed.html](part1_fixed.html)) with JS computing screen coordinates on hover ([part3.html](part3.html)), which escapes the table's clipping/stacking entirely. Verified via `document.elementFromPoint` hit-testing (not just visual) — confirmed the fix by checking the exact coordinate where the Copy button sits now returns the button itself instead of an underlying row's link.

## Take Profit tooltip fix, round 2 — the real fix (2026-08-30)

The `position: fixed` change above was insufficient: the tooltip was still a DOM descendant of the sticky ticker `<td>`, which establishes its own stacking context (`position: sticky` + `z-index: 3`). `position: fixed` only changes the layout/positioning reference (viewport instead of nearest positioned ancestor) — it does NOT exempt an element from its ancestor's stacking context for paint order. So the tooltip still lost the paint tie-break (same z-index: 3) to *later* rows' sticky columns (later in DOM order wins ties), which is exactly the clipped/occluded look the user reported a second time (confirmed via screenshot on SURG).

**Actual fix** ([part3.html](part3.html)): on hover, the tooltip node is physically reparented to `document.body` (not just repositioned), escaping the table's DOM tree — and therefore its stacking context — entirely. Show/hide is now fully JS-driven (mouseenter/mouseleave with a 150ms hide delay so moving the pointer from badge to tooltip doesn't close the gap between them) since CSS `:hover` ancestor-matching stops working once the node is reparented. On hide, the tooltip is moved back to its home badge (`tooltip._homeBadge`) to keep `badge.querySelector('.pf-tooltip')` working elsewhere.

Verified via `elementFromPoint` hit-testing at the exact SURG scenario from the user's screenshot (row deep in a filtered list, tooltip overlapping several rows below): copy button and left-edge content both now correctly resolve to the tooltip itself, not the underlying row.
